# 자동 진행 백로그 (매일 아침 루틴이 읽는 파일)

매일 아침 8시 자동으로 도는 **만물인테리어 운영점검 + 개발** 루틴이 이 파일을 읽고,
`[자동가능]` 표시가 붙은 항목 중 **맨 위 미완료 1건**을 골라 진행한다.
하루 1건이므로 아래 대기 항목이 대략 일주일치다.

> **왜 목록으로 두는가** — "알아서 개발해줘"라고 열어두면 매번 다른 곳을 건드려
> 사장님이 쓰는 기능이 흔들린다. 무엇을 할지 먼저 여기 적어두고, 루틴은 그 안에서만 움직인다.

## 루틴이 지켜야 할 규칙

1. **한 번에 1건만.** 욕심내지 않는다. 남는 시간엔 점검 결과를 자세히 적는다.
2. 시작 전 그 항목이 **아직 유효한지 확인**한다. 이미 고쳐졌으면 `[x]`로 체크만 하고 다음으로.
3. 손대기 전과 후에 **전체 회귀를 돌린다.** 손대기 전이 이미 빨간불이면 그걸 먼저 보고하고 멈춘다.
4. **main 에 직접 푸시 금지.** 작업 브랜치에 올리고 PR을 연다.
   PR 도구가 없는 세션이면 브랜치만 올리고 브랜치명을 보고한다.
5. 아래는 **절대 자동으로 하지 않는다** — 사장님 승인 없이는 손대지 않는다:
   - 저장 데이터 구조(serializeData/applyData) 변경
   - 고객에게 실제로 나가는 발송(문자·알림톡·메일) 켜기
   - 외부 서비스 설정·키 변경, 요금이 발생하는 설정
   - 사장님이 매일 쓰는 화면의 동작·배치 변경
6. 회귀가 깨졌는데 **원인을 못 찾으면 되돌리고 보고**한다. 억지로 밀어붙이지 않는다.
7. 새로 발견한 결함은 직접 고치지 말고 **이 파일 맨 아래 '발견' 절에 추가**만 한다(다음 후보).
8. **대기 목록이 비면 개발은 건너뛴다.** 할 일을 새로 만들어내지 말고 점검만 하고 마친다.

## 매일 하는 운영 준비 점검 (코드 변경 없음)

돈 벌 준비가 되어 있는지 확인한다. 하나라도 빨간불이면 **그게 최우선 보고 사항**이다.

**저장소만 있으면 되는 것 — 매일 반드시 수행**

- [ ] 상담 접수 경로가 유지되는가 — `data/config.json` 의 `forms.enabled=true` + `endpoint`·`accessKey` 존재
      (이게 꺼지면 **손님 문의가 다시 새기 시작한다**. 이 항목이 빨간불이면 다른 무엇보다 먼저 알려라)
- [ ] 접수 판정 일치 — `node scripts/ensure-lead-route-parity.mjs`
- [ ] 무결성 스크립트 전부 통과 — `for f in scripts/*.mjs; do node "$f"; done`
- [ ] 계약 서버 회귀 통과 — `cd contract-backend && npm test`
- [ ] 최근 커밋에 마무리 안 된 작업이나 회귀 위험이 없는가 — `git log --since=2.days`

**바깥 서비스 생존 확인 — 막히면 그냥 넘어갈 것**

⚠️ 이 세션의 네트워크 정책이 외부 접속을 막고 있을 수 있다(실측: `manmool-contract.fly.dev`·
`01023978629.github.io` 둘 다 프록시가 403으로 차단). **차단되면 우회하지 말고 "확인 불가"로 한 줄만
적고 넘어가라.** 매일 같은 실패를 길게 쓰지 마라.

- [ ] 홈페이지 — `curl -sS -m 20 -o /dev/null -w '%{http_code}' https://01023978629.github.io/manmool/`
- [ ] 계약 서버 — `curl -sS -m 30 https://manmool-contract.fly.dev/healthz`
      (Fly.io 절전 설정이라 첫 응답이 느릴 수 있다. 타임아웃을 넉넉히 주고, 느린 것과 죽은 것을 구분하라)
      · `live:false` 는 아직 정상(알림톡 설정 대기). 한 줄로만 적고 매일 반복 설명하지 마라.

> **더 나은 방법이 백로그에 있다** — 바깥 서비스 생존 확인은 인터넷이 열려 있는
> 구글 Apps Script 파수꾼이 맡는 게 맞다(백로그 11번). 그게 되기 전까지는 이 절이 임시방편이다.

### [자동가능] 4. 데모 화면의 '있지도 않은 직원'을 정직하게 고치기 ★신뢰
`js/as.js:12-20` 의 RULE 이 하자 유형마다 담당을 `정설비(설비)`·`이전기(전기)`·`박목공(목공)`·
`김현장(현장소장)`·`청소팀` 으로 배정한다. **만물인테리어는 1인 업체다.**
`data/project.json` 에도 `managerPhone` 같은 가짜 조직 정보가 있다.
이 화면들은 noindex 라 검색엔 안 뜨지만 링크로는 열리고, 손님이 보면 사실과 다르다.
→ 담당자 이름을 실제 운영에 맞게 바꾼다(예: `대표 직접 확인`, `협력 설비팀`).
   없는 사람 이름·직책을 새로 지어내지 말 것. 확신이 안 서면 중립적인 표현으로.
   demo 배너 문구도 손님이 오해하지 않게 다듬는다.

### [자동가능] 5. 손님이 모르는 내부 용어를 손님 말로 바꾸기
상담 폼 바로 옆 운영 프로세스 섹션에 `n8n` 같은 내부 기술 용어가 그대로 노출된다.
첫 화면 아래 숫자 4칸도 `무승인 발송 0건` 처럼 손님이 뜻을 모르는 내부 지표다.
`data/site.json` 의 해당 문구를 **손님이 쓰는 말**로 바꾼다.
→ 숫자·사실 자체는 바꾸지 말고 **표현만** 바꾼다. 없는 실적을 지어내지 말 것.
   예: '무승인 발송 0건' → '연락 전 항상 대표 확인' 처럼 뜻이 통하는 말로.
   확신이 안 서는 항목은 손대지 말고 '발견' 절에 적어 사장님께 물을 것.

### [자동가능] 6. '시공 사례'라는 이름이 거짓말하는 것 정리
블로그·글 페이지 9곳이 '시공 사례'로 링크하는데 도착지는 **AI 추천 디자인 시안**이고,
정작 그 섹션은 스스로 'AI 시안'이라고 밝히고 있다. 이름과 내용이 어긋난다.
→ 링크 문구를 도착지에 맞게 바꾼다(예: 'AI 디자인 제안 보기').
   **실제 시공 사진을 새로 만들어내지 말 것** — 없는 걸 있다고 하면 안 된다.
   진짜 시공 사례 섹션이 필요하다는 점은 '발견' 절에 남겨 사장님과 상의한다.

### [자동가능] 7. 서비스 지역을 본문에 적기
지역 업체인데 본문에 서비스 지역이 없다. `index.html` 의 `#contact` 근처에
`<h3>서비스 지역</h3><p>대전 중구·서구·유성구·대덕구·동구, 세종시 전역</p>` 같은 정적 블록 추가.
근거: `index.html` JSON-LD 의 `areaServed`(대전·세종·충남) 하위 집합이라 **새 사실이 아니다.**
순수 정적 HTML만 추가 — 빌드 도구·외부 의존성 불필요.

### [자동가능] 9. 디자인 시안에 고유 주소 만들기
240개 시안이 전부 `index.html` 모달 안에만 있어 **고유 URL·고유 title 이 하나도 없다.**
검색으로 들어올 진입점이 홈 하나뿐이다.
→ 최소한 해시 라우팅(`#design=<slug>`)이라도 붙여 공유·재방문이 되게 한다.
   더 나아가려면 `scripts/prerender-posts.py` 방식으로 대표 시안 몇 개만 정적 페이지화.
   **한 번에 다 하려 하지 말고 해시 라우팅까지만** 하고 나머지는 '발견'에 남길 것.

### [자동가능] 10. 폰 본문 글씨 마무리
접근성 작업에서 주요 항목은 15px 로 올렸으나, 아직 13.5~14px 로 남은 본문이 있는지
`css/styles.css` 를 훑어 확인하고 640px 블록에서 올린다.
→ 제목·배지·캡션처럼 작아야 자연스러운 것은 그대로 둔다. **본문 성격의 글만.**
   데스크톱 레이아웃은 건드리지 말 것.

### [PC필요] 11. 파수꾼이 서비스 생존까지 확인하게 하기
주간 루틴이 도는 환경은 외부 접속이 막혀 있어 홈페이지·계약 서버가 살아 있는지 확인하지 못한다.
반면 구글 Apps Script 파수꾼은 **인터넷이 열린 구글 서버에서 매일 아침 돈다.**
→ `apps-script/Watchdog.gs` 에 하루 1회 생존 확인을 추가:
   - `UrlFetchApp.fetch` 로 홈페이지 200 여부, 계약 서버 `/healthz` 의 `ok`
   - 죽어 있으면 그날 캘린더 알림 맨 위에 `⚠️ 홈페이지 응답 없음` 처럼 얹는다
   - **실패해도 파수꾼 본체가 죽지 않게** 각각 try/catch, `muteHttpExceptions:true`, 짧은 타임아웃
   - Fly.io 는 절전이라 첫 응답이 느리다 — 느린 것과 죽은 것을 구분할 것
가치: 홈페이지가 죽으면 그날부터 문의가 0이 되는데 지금은 알 방법이 없다.

⚠️ **자동으로 하지 말 것.** Watchdog.gs 를 고치면 사장님이 Apps Script 에 다시 붙여넣어야 하고,
그 작업은 폰에서 꽤 번거롭다. 사장님이 PC 를 쓰는 세션에서 함께 처리한다.
