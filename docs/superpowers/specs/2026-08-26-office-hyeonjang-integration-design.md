# 관리사무소 접수와 현장 웹 아파트 오더 연동 설계

## 문서 상태

- 상태: 사용자 승인 설계
- 작성일: 2026-08-26
- 대상 서비스:
  - 공개 영업 사이트 `manmool`
  - 내부 현장 운영 PWA `hyeonjang`
  - 기존 Google Apps Script Drive 중계 서버
- 선행 결정: 관리사무소 직원만 접수한다. 입주민 직접 접수는 이번 범위에서 제외한다.
- 대체 관계: 이 문서는 기존 문자 전용 `office-request.html` 설계를 대체한다. 기존 로컬 구현은 공개 배포되지 않았으며, 자동 연동 구현 시 새 설계에 맞게 수정한다.

## 1. 목적

관리사무소 직원이 단지 전용 화면에서 보수 업무를 접수하면, 만물인테리어 대표가 사용하는 현장 웹의 `아파트 오더`에 안전하게 전달되도록 한다. 접수 이후 방문, 작업, 완료, 청구, 입금 상태는 현장 웹에서 관리하고 관리사무소에는 자기 단지의 필요한 정보만 돌려준다.

핵심 목표는 다음과 같다.

1. 관리사무소 직원의 접수 입력을 대표가 다시 옮겨 적지 않는다.
2. 접수, 사진, 일정, 결과 보고가 하나의 접수번호로 연결된다.
3. 관리사무소는 자기 단지 자료만 볼 수 있다.
4. 현장 웹의 기존 프로젝트, 사진, 견적, Drive 동기화 동작을 깨뜨리지 않는다.
5. GitHub Pages에 비밀번호, 내부 토큰, 전체 고객 자료를 노출하지 않는다.

## 2. 범위

### 포함

- 단지별 전용 접수 주소
- 6자리 비밀번호 로그인
- 8시간 유효한 임시 세션
- 관리사무소 직원의 신규 접수, 검토 전 수정·취소, 자기 단지 상태 조회
- 접수 사진 최대 5장
- Apps Script의 접수 전용 저장소와 API
- 현장 웹 신규 접수 배지와 `아파트 오더` 변환
- 접수와 현장 오더의 상태 동기화
- 긴급 접수의 대표 Google Calendar 알림
- 완료 사진과 간략 보고서의 관리사무소 공유
- 보안, 오류 복구, 데이터 보존, 회귀검사, 단계별 배포와 원복

### 제외

- 입주민 직접 접수
- Google 계정이나 별도 회원가입
- 관리사무소 간 자료 공유
- 자동 SMS, 카카오 알림톡, 유료 푸시 서비스
- 관리사무소의 견적·일정·입금 상태 직접 변경
- 협력업체 계정과 기사 전용 계정
- HOME DOC의 운영관리·영업 키트·샘플 대시보드를 그대로 공개하는 일
- 현장 웹 전체 상태 파일을 관리사무소 브라우저에 내려주는 일

## 3. 선택한 접근법

기존 Apps Script 중계 서버를 확장하고, 현장 웹의 기존 `aptOffices`와 `aptOrders`를 연동한다.

문자 접수 후 수동 등록은 입력 중복과 누락이 많아 제외한다. HOME DOC를 별도 플랫폼으로 운영하는 방식은 기능과 데이터가 중복되고 GitHub Pages의 공개 범위가 커지므로 제외한다.

## 4. 전체 구조

```text
관리사무소 직원
  │ 단지 전용 주소 + 6자리 비밀번호
  ▼
manmool 관리사무소 접수 화면
  │ HTTPS, 임시 세션, 접수 데이터·압축 사진
  ▼
Apps Script 접수 전용 API
  ├─ 단지 인증·세션
  ├─ 접수번호·중복 방지
  ├─ 관리사무소접수.json
  └─ 관리사무소접수/{단지}/{접수번호}/ 사진 폴더
  │ 내부 APP_TOKEN으로만 신규 접수 조회
  ▼
hyeonjang 신규 관리사무소 접수함
  │ 대표 승인
  ▼
기존 아파트 오더
  │ 상태·방문일·공개금액·완료자료 갱신
  └───────────────────────────────┐
                                  ▼
                    관리사무소 자기 단지 상태 화면
```

접수 전용 저장소는 `현장데이터.json`과 분리한다. 관리사무소 요청이 내부 전체 상태 파일의 revision을 직접 바꾸지 못하게 하고, 현장 웹이 명시적으로 승인한 접수만 기존 `aptOrders`에 넣는다.

## 5. 구성요소 책임

### 5.1 `manmool` 공개 영업 페이지

`office.html`은 관리사무소 대상 영업·제휴 안내 페이지로 유지한다.

- 기존 서비스 소개, 사례, 전화·문자 문의를 유지한다.
- `관리사무소 업무 접수` 버튼을 추가한다.
- 버튼은 단지 전용 주소를 가진 직원만 사용하는 인증 화면으로 이동한다.
- 입주민용 공개 접수로 오해하지 않도록 “관리사무소 직원 전용”이라고 명시한다.

### 5.2 관리사무소 인증·접수 화면

접수 화면은 모바일 우선으로 구성한다.

주요 화면:

1. 단지 확인과 6자리 비밀번호 입력
2. 업무 현황: 신규, 진행 중, 완료
3. 새 작업 접수
4. 접수 상세와 처리상태
5. 완료 사진·간략 보고서
6. 담당자 정보와 비밀번호 변경 요청

단지명은 URL의 공개 식별자에서 정하고 사용자가 다른 단지를 선택하지 못하게 한다. URL 식별자는 인증 수단이 아니며 비밀번호와 서버 검증을 반드시 거친다.

### 5.3 Apps Script 접수 전용 API

기존 Drive relay와 같은 Apps Script 프로젝트를 사용하되, 관리사무소 세션과 내부 `APP_TOKEN`을 분리한다.

접수 전용 API는 다음 책임만 가진다.

- 단지와 비밀번호 검증
- 단기 세션 발급·검증
- 접수 데이터 구조와 길이 검증
- 접수번호 생성과 중복 방지
- 접수 목록·상세의 단지별 필터
- 사진 파일 검증·저장
- `LockService`를 사용한 접수번호 발급과 JSON 갱신 직렬화
- 현장 웹 내부 조회·상태 갱신
- 보안 이벤트와 동기화 오류 기록

### 5.4 현장 웹

기존 `더보기 → 아파트 오더`를 확장한다.

탭:

- 신규 접수
- 방문예정·진행중
- 완료·청구
- 단지·접근권한 설정

신규 접수에서 대표는 다음 동작을 할 수 있다.

- `아파트 오더 등록`
- `내용 보완 요청`
- `보류`
- `전화`
- `사진 확인`

오더 등록 시 기존 프로젝트에 연결하거나 새 프로젝트를 만들 수 있다. 접수번호를 `sourceRequestId`로 저장하고 사진과 완료 보고서도 이 번호로 추적한다.

## 6. 관리사무소 입력 항목

필수:

- 작업 위치: 동·호수 또는 공용부 위치
- 작업 종류: 누수, 배수, 급수, 난방, 방수, 공용시설, 기타
- 긴급도: 일반 또는 긴급
- 증상·요청사항
- 관리사무소 담당자 이름
- 관리사무소 담당자 전화번호
- 개인정보 수집·이용 확인

선택:

- 배관 종류: 미확정, 오수, 우수, 잡배수, 난방, 급수
- 희망 방문일
- 입주민 이름·연락처
- 현장 사진 최대 5장

입주민 연락처는 입주민이 제공에 동의한 경우에만 입력한다. 기본 연락 창구는 관리사무소 담당자다.

## 7. 데이터 모델

### 7.1 관리사무소 단지

```json
{
  "officeId": "office_...",
  "slug": "sample-apt",
  "complexName": "예시 아파트",
  "pinHash": "[SERVER_ONLY]",
  "pinSalt": "[SERVER_ONLY]",
  "enabled": true,
  "contactName": "관리사무소 담당자",
  "contactPhone": "010-0000-0000",
  "createdAt": "2026-08-26T00:00:00+09:00",
  "updatedAt": "2026-08-26T00:00:00+09:00"
}
```

`pinHash`와 `pinSalt`는 Script Properties 또는 서버 전용 설정에만 두고 공개 응답이나 Drive 공개 파일에 포함하지 않는다.

`officeId`는 현장 웹의 기존 `aptOffices` ID를 기준으로 한 번만 생성해 서버와 현장 웹에서 함께 사용한다. 단지 생성·변경은 내부 `APP_TOKEN`으로 인증된 현장 웹만 할 수 있고, 공개 `slug` 변경으로 `officeId`가 바뀌지 않는다.

### 7.3 현장 웹 `aptOrders` 확장

기존 필드는 유지하고 다음 필드만 추가한다.

```json
{
  "source": "office-intake",
  "sourceRequestId": "req_...",
  "receiptNo": "MM-20260826-0001",
  "officeContactName": "홍길동",
  "officeContactPhone": "010-0000-0000",
  "residentContact": null,
  "urgency": "normal",
  "location": "욕실 천장",
  "preferredVisitDate": "2026-08-27",
  "intakePhotoIds": ["drive-file-id"]
}
```

`sourceRequestId`에는 고유 제약을 적용하는 것과 같은 효과를 내도록 생성 전 기존 오더를 검색한다. 같은 접수를 다시 가져와도 새 오더를 만들지 않는다.

## 8. 상태 규칙

| 접수 상태 | 관리사무소 표시 | 현장 웹 상태 |
|---|---|---|
| `pending_review` | 접수됨 | 신규 접수 |
| `needs_info` | 내용 확인 필요 | 보완 요청 |
| `accepted` | 확인 완료 | 접수 `recv` |
| `visit_scheduled` | 방문 예정 | 방문예정 `visit` |
| `in_progress` | 작업 중 | 진행중 `work` |
| `completed` | 작업 완료 | 완료 `done` |
| `billed` | 청구 완료 | 청구됨 `billed` |
| `paid` | 처리 완료 | 입금완료 `paid` |
| `on_hold` | 확인 중 | 보류 |
| `cancelled` | 취소됨 | 취소, 오더 미생성 또는 종료 |

관리사무소는 검토 전 접수를 수정·취소할 수 있다. 대표가 승인한 뒤에는 보완 요청 또는 전화 협의로 변경한다. 견적, 일정, 작업, 청구, 입금 상태는 대표만 바꿀 수 있다.

## 9. API 계약

모든 POST는 기존 Apps Script 제약에 맞춰 `Content-Type: text/plain;charset=utf-8`의 JSON 문자열을 사용한다.

### 9.1 관리사무소 세션 API

#### `officeLogin`

요청:

```json
{
  "action": "officeLogin",
  "ts": 1787700000000,
  "payload": {
    "slug": "sample-apt",
    "pin": "123456"
  }
}
```

성공 응답에는 단지명과 8시간 유효한 서명 세션 토큰을 돌려준다. 비밀번호 원문은 로그나 저장소에 남기지 않는다.

#### `officeList`, `officeGet`, `officeCreate`, `officeUpdate`, `officeCancel`, `officeUpload`

- 세션 토큰과 요청 시각을 검증한다.
- 세션의 `officeId`를 서버에서 사용한다.
- 클라이언트가 보낸 `officeId`로 권한 범위를 넓히지 않는다.
- `officeUpdate`와 `officeCancel`은 `pending_review`, `needs_info` 상태에서만 허용한다.
- `officeUpload`는 자기 단지·자기 접수에만 파일을 추가한다.

### 9.2 현장 웹 내부 API

#### `officeInbox`

- 내부 `APP_TOKEN`이 필요하다.
- `pending_review`, `needs_info`, 동기화 재시도 대상을 가져온다.
- cursor 또는 `updatedAfter`로 증분 조회한다.

#### `officeAccept`

- 내부 `APP_TOKEN`이 필요하다.
- `requestId`, `hyeonjangOrderId` 연결을 원자적으로 기록한다.
- 기존 연결이 있으면 기존 결과를 반환한다.

#### `officeSetStatus`

- 내부 `APP_TOKEN`이 필요하다.
- 허용된 상태 전이만 적용한다.
- 관리사무소 공개금액, 방문일, 완료 보고서 공개 여부를 별도 필드로 받는다.

#### `officeAdminUpsert`, `officeRotatePin`, `officeDisable`

- 내부 `APP_TOKEN`이 필요하다.
- 기존 `aptOffices`의 안정적인 ID로 단지를 생성·갱신한다.
- 비밀번호 변경 시 session version을 올려 기존 세션을 즉시 무효화한다.
- 단지 비활성화는 신규 로그인·접수를 막되 기존 자료를 삭제하지 않는다.

## 10. 인증과 보안

### 10.1 단지 비밀번호

- 숫자 6자리
- 무작위 생성, 단지마다 다르게 발급
- 해시와 무작위 소금값만 서버에 저장
- 원문은 생성 직후 한 번만 관리자에게 전달
- 변경 시 기존 세션을 모두 무효화

### 10.2 세션

- 서버 비밀키로 서명
- `officeId`, 발급시각, 만료시각, session version 포함
- 8시간 후 만료
- 브라우저 `sessionStorage`에만 저장
- 로그아웃, 비밀번호 변경, 단지 비활성화 시 무효

### 10.3 로그인 제한

- 단지별 연속 5회 실패 시 10분 제한
- 성공 시 실패 횟수 초기화
- 제한 응답은 단지 존재 여부를 노출하지 않는 동일 문구 사용
- Apps Script에서 신뢰할 수 있는 IP를 얻기 어렵기 때문에 IP 기반 보안에 의존하지 않는다.

### 10.4 입력·파일 제한

- 단지·세션·상태 권한을 서버에서 재검증
- 자유 입력은 항목별 최대 길이 적용
- 전화번호 형식 정규화
- MIME과 파일 시그니처를 함께 확인
- 허용 이미지: JPEG, PNG, WebP
- 브라우저에서 장변 1,600px 이하로 줄인 뒤 서버에서 한 장 2MB 이하 재검증
- 접수당 최대 5장
- 파일명은 접수번호와 순번으로 서버가 생성

### 10.5 비밀정보 경계

- 기존 내부 `APP_TOKEN`은 관리사무소 브라우저에 전달하지 않는다.
- 단지 비밀번호, 내부 토큰, 세션 서명키는 GitHub에 저장하지 않는다.
- 문서, 대화, 로그에는 비밀값 대신 `[REDACTED_SECRET]`을 사용한다.
- 접수 목록 응답은 자기 단지 자료만 포함하고 내부 전체 상태 파일을 반환하지 않는다.
- 관리사무소 페이지에는 CSP를 적용하고 사용자 입력을 문자열 결합 `innerHTML`로 표시하지 않는다.
- 화면 출력과 보고서 생성 시 모든 사용자 입력을 이스케이프한다.

## 11. 알림

- 일반 접수: 현장 웹 상단 `관리사무소 신규 접수 N건` 배지
- 긴급 접수: 배지와 함께 대표 Google Calendar 일정 생성
- 24시간 미확인 접수: 현장 웹 경고 표시
- 내용 보완 요청: 관리사무소 상태 화면에 표시
- 알림 실패는 접수를 취소하지 않는다.
- 캘린더 알림 생성 실패는 보안 로그가 아닌 운영 오류 목록에 남긴다.

## 12. 사진과 완료 보고서

- 접수 사진은 `관리사무소접수/{단지 slug}/{접수번호}/`에 저장한다.
- 현장 웹에서 오더를 승인할 때 파일 ID를 `intakePhotoIds`에 연결한다.
- 이후 작업 전·후 사진은 기존 현장 웹 사진 흐름을 사용한다.
- 완료 보고서는 작업명, 방문일, 처리내용, 공개금액, 공개 승인된 전·후 사진만 포함한다.
- 동·호수, 전화번호가 홍보 후기나 공개 사례에 자동 포함되지 않게 한다.

## 13. 오류 처리와 복구

### 접수 화면

- 서버가 접수번호를 반환한 경우에만 완료로 표시한다.
- 네트워크 오류 시 입력값을 현재 화면 메모리에 유지하고 재시도를 제공한다.
- 서버가 같은 `idempotencyKey`를 받으면 기존 접수번호를 반환한다.
- 사진 업로드가 일부 실패하면 접수 완료로 넘기지 않고 실패한 사진만 재시도한다.
- 서버 장애 시 대표 전화 접수 안내를 제공한다.

### 현장 웹

- 접수 원본을 먼저 보존하고 오더 변환 실패를 `동기화 필요`로 남긴다.
- 재시도 전에 `sourceRequestId`로 기존 오더를 찾아 중복을 막는다.
- 상태 회신 실패는 로컬 재시도 큐에 남기고 다음 온라인 연결에서 다시 보낸다.
- 기존 Drive 저장 revision 충돌 규칙을 우회하거나 무조건 덮어쓰지 않는다.

### 운영 중단과 원복

- Script Property `OFFICE_INTAKE_ENABLED=0`으로 신규 로그인·접수만 중단한다.
- 현장 웹 기존 프로젝트, 사진, 견적, 아파트 오더는 계속 사용 가능해야 한다.
- 관리사무소 버튼을 숨겨도 기존 접수 데이터는 삭제하지 않는다.
- 원복 시 삭제 대신 이전 정적 페이지와 Apps Script 배포 버전으로 되돌린다.

## 14. 데이터 보존과 개인정보

- 취소·거절된 접수: 90일 후 삭제 대상
- 완료된 일반 접수: 완료일로부터 1년
- 계약·세무 증빙으로 전환된 자료: 관련 법정 보관기간
- 만료 자료는 자동 영구삭제부터 구현하지 않고, 만료 목록을 관리자에게 보여 준 뒤 확인 후 정리하는 방식으로 시작한다.
- 감사 로그에는 접수번호, 단지 ID, 동작, 결과, 시각만 기록하고 비밀번호와 전체 전화번호는 기록하지 않는다.
- `privacy.html`에 관리사무소 직원 접수의 수집 항목, 목적, 보존기간, 처리 경로를 구분해 명시한다.

## 15. 파일과 저장소 경계

### `manmool`

- `office.html`: 직원 전용 접수 진입점과 설명
- `office-request.html`: 로그인, 현황, 접수 화면 구조
- `css/office-request.css`: 모바일 우선 화면 스타일
- `js/office-request-core.js`: 검증, 상태 표현, API 요청 데이터 생성
- `js/office-request.js`: 세션, 화면 전환, 재시도, 사진 압축
- `privacy.html`: 관리사무소 접수 개인정보 처리
- Pages 산출물 스크립트: 새 페이지 포함, 비밀값 제외 검사
- 정적·브라우저 테스트

### `hyeonjang`

- `apps-script/Code.gs`: 접수 전용 API와 내부 inbox/status 액션
- `apps-script/Pure.gs` 또는 동등한 순수 모듈: 인증·검증·상태 전이·중복 방지 계산
- `index.html`: 신규 접수함, 아파트 오더 연결, 상태 회신, 동기화 오류 UI

Apps Script 배포는 GitHub Pages 배포와 별도다. 정적 파일을 배포했다고 Apps Script 변경이 적용된 것으로 간주하지 않는다.

## 16. 테스트 전략

### 순수 함수 단위검사

- 전화번호, 날짜, 입력 길이, 이미지 형식 검증
- 비밀번호 해시 검증
- 세션 발급·만료·버전 무효화
- 단지별 자료 필터
- 접수번호와 idempotency 규칙
- 허용·거절 상태 전이
- `sourceRequestId` 중복 오더 방지

### API 계약검사

- 올바른 단지 로그인
- 잘못된 비밀번호 5회와 10분 제한
- 만료·변조 세션 거절
- 다른 단지 자료 조회·수정·사진 업로드 거절
- 내부 API의 잘못된 `APP_TOKEN` 거절
- 파일 크기·MIME·개수 제한
- 접수 생성, 재전송, 오더 연결, 상태 회신

### 브라우저검사

- 390px 모바일에서 가로 넘침 없음
- 주요 버튼 높이 44px 이상
- 로그인, 신규 접수, 사진 5장, 접수번호 확인
- 검토 전 수정·취소
- 세션 만료와 재로그인
- 오프라인·서버 오류·사진 일부 실패와 재시도
- 자기 단지 상태 목록만 표시

### 현장 웹 회귀검사

- 기존 `aptOffices`, `aptOrders` 등록·수정·상태 변경
- 기존 프로젝트 생성과 사진 연결
- 견적, 일정, Drive load/save, revision 충돌
- 관리사무소 접수 승인 후 오더 한 건만 생성
- 접수 사진의 올바른 오더·프로젝트 연결
- 상태 변경의 관리사무소 화면 반영

### 실제 계정·기기 확인

- 테스트 단지 비밀번호 발급
- 실제 PC와 휴대전화에서 로그인·사진 접수
- 현장 웹에서 신규 배지, 승인, 상태 변경
- 관리사무소 휴대전화에서 상태와 완료 보고서 확인

## 17. 배포 순서

1. Apps Script 순수 함수와 계약검사 통과
2. 접수 전용 Script Properties 생성
3. Apps Script 새 웹앱 버전 배포
4. 테스트 단지와 6자리 비밀번호 생성
5. 현장 웹 신규 접수함과 오더 연동 배포
6. 현장 웹 live 빌드 마커와 relay health 확인
7. 관리사무소 인증·접수 페이지 배포
8. PC·휴대전화 전체 흐름 시험
9. 접수→승인→방문예정→완료→보고서 확인
10. 실제 관리사무소별 전용 주소와 비밀번호 발급

각 저장소와 Apps Script는 별도 승인·배포 단위로 다룬다. 한 단계가 실패하면 다음 단계를 공개하지 않는다.

## 18. 완료 기준

- 관리사무소 직원이 전용 주소와 비밀번호로 자기 단지에 로그인할 수 있다.
- 다른 단지의 접수·사진·금액을 조회하거나 수정할 수 없다.
- 신규 접수와 최대 5장 사진이 서버 접수번호로 저장된다.
- 같은 요청을 재전송해도 현장 오더가 하나만 생긴다.
- 대표가 신규 접수를 확인하고 기존 아파트 오더로 변환할 수 있다.
- 방문예정, 진행중, 완료, 청구, 입금완료 상태가 관리사무소 화면에 반영된다.
- 현장 웹 기존 데이터 저장과 사진·견적 기능의 회귀검사가 통과한다.
- 비밀번호와 내부 `APP_TOKEN`이 GitHub 산출물, 로그, 테스트 결과에 노출되지 않는다.
- Apps Script, 현장 웹, 관리사무소 페이지의 실제 배포본 전체 흐름이 PC와 휴대전화에서 검증된다.
- 신규 접수 기능을 꺼도 기존 현장 웹 운영은 계속된다.

## 19. 구현 단계 분리

구현은 다음 세 묶음으로 나눈다.

1. **접수 서버 기반**: 데이터 모델, 인증, 세션, API, Drive 저장, 테스트 단지
2. **현장 웹 연동**: 신규 접수함, 오더 변환, 상태 회신, 사진 연결, 알림
3. **관리사무소 화면**: 로그인, 접수, 목록, 상태, 완료 보고서, 개인정보 안내

각 묶음은 이전 묶음의 계약검사가 통과한 뒤 진행한다. 구현 계획은 이 설계 문서의 사용자 검토와 승인 후 별도로 작성한다.
