# 만물 관리사무소 포털 최근 변경센터 R1 설계

## 문서 상태

- 상태: 대화 설계 승인 완료, 서면 명세 사용자 검토 대기
- 작성일: 2026-08-30
- 대상 저장소: `manmool`
- 기준 커밋: `aadf328f159596d23d4ca521b69a53655aa6227e` (`origin/main`)
- 사용자 기능 대상: `office-request.html` 관리사무소 전용 접수 포털
- 다음 단계: 이 문서 승인 후 `writing-plans` 절차로 파일별 구현 계획 작성

## 1. 목적

관리사무소 직원이 포털을 새로고침했을 때 직전 성공 조회 이후 어떤 접수가 달라졌는지 빠르게 파악하게 한다. 첫 릴리스는 기존 `officeList` 응답만 사용하며, 관리사무소가 직접 누르는 수동 새로고침에만 반응한다.

이 기능의 `최근 변경`은 실시간 알림, 읽음 확인 또는 서버에 저장되는 알림 이력이 아니다. 현재 탭에서 직전 성공 조회와 이번 성공 조회를 비교한 임시 안내다. 탭을 닫거나 페이지를 새로 불러오거나 로그아웃하면 비교 기준은 사라진다.

## 2. 성공 기준

- 최초 로그인 또는 세션 복원 뒤의 첫 성공 목록은 비교 기준만 만들고 변경 목록을 표시하지 않는다.
- 두 번째 이후 사용자의 수동 새로고침에서 이번 목록에 새로 나타난 접수와 상태·갱신시각 변화를 구분해 표시한다.
- 최근 변경 카드에서 기존 상세 화면으로 이동할 수 있다.
- 새로고침 실패, 로그아웃, 세션 만료와 응답 순서 역전이 기존 목록이나 개인정보를 잘못 노출하지 않는다.
- 최근 변경 자료는 브라우저 영구 저장소, URL, 로그 또는 외부 서비스에 기록되지 않는다.
- 기존 접수 생성·수정·취소·사진·완료보고·인증 흐름과 공개 API 계약은 그대로 유지된다.
- 390px 모바일 화면과 키보드·스크린리더 사용 환경에서 기능을 조작할 수 있다.

## 3. 고정 범위

### 3.1 사용자 화면

`officeDashboardView` 상단에 다음 요소를 추가한다.

1. `목록 새로고침` 버튼
2. `🔔 최근 변경` 요약 영역
3. 마지막 성공 확인 시각
4. 최근 변경이 없을 때의 명확한 빈 상태
5. 최근 변경 최대 10건과 초과 건수 안내

새로고침 버튼은 실제 `<button type="button">`으로 구현한다. 사용자가 누른 경우에만 기존 `officeList`를 한 번 호출한다. 자동 polling, 페이지 가시성 이벤트 조회, 온라인 복귀 자동 조회, 브라우저 알림은 추가하지 않는다.

### 3.2 비교 대상

비교 대상은 현재 필터로 보이는 카드가 아니라 성공한 `officeList` 응답 전체다. 현재 서버가 단지별로 반환하는 최근 최대 50건 범위 안에서만 비교한다. 필터를 바꾸더라도 현재 탭의 비교 기준과 최근 변경 목록은 유지된다.

첫 성공 응답은 기준 스냅샷이 된다. 이후 성공한 수동 새로고침은 직전 성공 스냅샷과 비교한 뒤, 이번 응답을 다음 비교의 새 기준으로 교체한다. 실패한 응답은 기준을 갱신하지 않는다.

### 3.3 변경 판정

행 식별 키는 `requestId`다. 기준 스냅샷에는 다음 값만 둔다.

- `requestId`
- `status`
- 검증을 통과한 `updatedAt`의 밀리초 값 또는 `null`

변경 판정은 다음 순서를 따른다.

1. 이전 기준에 없는 유효한 `requestId`가 나타나면 `새로 확인된 접수`다.
2. 같은 `requestId`의 `status`가 달라지면 상태 변경이다. `updatedAt`이 같거나 잘못되어도 상태 변경은 감지한다.
3. 상태는 같고 이전·현재 `updatedAt`이 모두 유효하며 현재 값이 이전보다 증가하면 `내용 갱신`이다.
4. 응답에서 사라진 `requestId`는 삭제·취소·권한 변경으로 추론하지 않으며 최근 변경에 넣지 않는다.
5. 상태와 유효한 시각이 모두 같으면 변경이 아니다.
6. 과거보다 작은 `updatedAt`만으로는 변경으로 판정하지 않는다.

새로 확인된 접수도 최초 기준 생성 때는 표시하지 않고, 이미 기준이 생긴 뒤 나타난 경우에만 표시한다. `officeList`는 최근 최대 50건만 반환하므로 이 표시는 서버 생성 시각을 증명하는 `신규 접수`가 아니다. 정확한 사용자 문구는 `이번 새로고침에서 새로 확인`으로 고정한다. 50건 범위 밖으로 밀렸다가 다시 나타난 기존 접수도 같은 문구를 사용하며 생성 시점을 추론하지 않는다.

### 3.4 상태별 표현

상태 라벨은 기존 `office-request-core.js`의 `statusLabel()`을 계속 사용한다. 최근 변경의 업무 표현은 다음처럼 고정한다.

| 조건 | 최근 변경 표현 |
|---|---|
| 새 `requestId` | 이번 새로고침에서 새로 확인 |
| `needs_info` | 자료 보완 필요 |
| `visit_scheduled` | 방문 예정 |
| `completed` | 작업 완료 |
| `billed` | 청구 완료 |
| `paid` | 입금 완료 |
| `cancelled` | 취소됨 |
| 그 밖의 상태 변경 | `statusLabel()`의 현재 상태 |
| 상태 동일, 유효한 `updatedAt` 증가 | 내용 갱신 |

최근 변경은 유효한 최신 `updatedAt` 내림차순으로 정렬한다. 유효한 시각이 없는 항목은 유효한 항목 뒤에 두고 서버 응답 순서를 유지한다. 같은 시각이면 서버 응답 순서를 유지한다.

### 3.5 중복과 잘못된 행

- 같은 `requestId`가 여러 번 오면 유효한 `updatedAt`이 가장 최신인 행 하나만 사용한다.
- 중복 행 모두의 시각이 잘못되었으면 서버 응답에서 먼저 나온 한 행만 사용한다.
- 서로 다른 중복 행의 필드를 합치지 않는다.
- 공백을 제거한 뒤 비어 있거나 120자를 초과하는 `requestId`는 비교와 최근 변경에서 제외한다.
- 응답 정규화를 시작할 때 `validationNow`를 한 번 고정한다. `updatedAt`은 시간대가 포함된 ISO 8601 문자열이고 `Date.parse()` 결과가 유한하며 `validationNow`보다 미래가 아닐 때만 유효하다. 미래 허용 오차는 두지 않는다.
- 누락·비정상·미래 `updatedAt`, 유효→무효 또는 무효→유효 전환은 상태가 같으면 시간 변화의 근거로 사용하지 않는다. 상태가 바뀌어 표시되는 경우 시각은 `시간 확인 필요`로 보여준다.

## 4. 화면 표시와 이동

최근 변경 한 건에는 승인된 최소 정보만 표시한다.

- 사람이 읽는 `receiptNo`
- 동·호 또는 공용부 위치
- 현재 상태 또는 변경 종류
- 변경 시각

`receiptNo`가 없으면 내부 `requestId`를 대신 노출하지 않고 `접수번호 확인 필요`로 표시한다. 위치가 없으면 `위치 확인 필요`로 표시한다. 문구는 모두 `textContent`로 넣고 길이를 제한한다.

접수번호와 동·호/공용 위치는 사용자가 승인한 인증 화면 내부의 최소 업무 식별정보이며 기존 접수 카드에도 이미 표시되는 값이다. 이 값은 최근 변경 비교 스냅샷에는 넣지 않고, 최신 `requests` 메모리에서 렌더링할 때만 읽는다. 인증되지 않은 화면, URL, 브라우저 저장소 또는 외부 알림에는 표시하지 않는다.

각 항목의 `상세 보기`는 기존 상세 화면을 열며 새 URL, query string, fragment 또는 history state를 만들지 않는다. 접수 상세를 보고 대시보드로 돌아와도 같은 문서가 유지되는 동안 기준 스냅샷은 유지된다. 브라우저 새로고침과 새 탭에서는 새 기준을 만든다.

최근 변경 항목의 `requestId`를 현재 `requests`에서 찾지 못하면 상세 API를 호출하거나 오래된 표시 자료로 상세를 재구성하지 않는다. `현재 목록에서 접수를 찾을 수 없습니다. 목록을 새로고침해 주세요.`라고 안내하고 대시보드를 유지한다.

최근 변경은 최대 10건만 렌더링하고, 초과하면 `외 N건의 변경이 있습니다`를 표시한다. `마지막 확인`은 서버 `updatedAt`이 아니라 가장 최근 성공 응답을 적용한 클라이언트 시각이다.

## 5. 상태와 데이터 흐름

프런트엔드 메모리에는 다음 상태만 추가한다.

- `listSnapshot`: 직전 성공 목록의 비교 허용 필드
- `recentChanges`: 이번 성공 비교 결과의 최소 참조 정보
- `lastSuccessfulRefreshAt`: 마지막 성공 응답 적용 시각
- `listGeneration`: 오래된 목록 응답 폐기용 세대 번호
- `refreshPending`: 새로고침 버튼 중복 실행 방지

초기 흐름은 다음과 같다.

1. 로그인 또는 세션 복원
2. 기존 `loadDashboard()`가 `officeList` 호출
3. 세션과 응답이 유효하면 목록 렌더링
4. `listSnapshot`이 없으므로 기준만 생성
5. 최근 변경은 비우고 `목록을 불러왔습니다`와 마지막 확인 시각 표시

수동 새로고침 흐름은 다음과 같다.

1. 현재 세션과 `sessionGeneration`을 고정
2. `listGeneration`을 증가시키고 버튼 비활성화
3. 기존 `authenticatedCall('officeList', {})` 실행
4. 응답 시 현재 세션과 최신 `listGeneration`인지 확인
5. 응답을 검증·중복 제거하고 직전 기준과 비교
6. 기존 요청 목록, 최근 변경, 새 기준, 마지막 성공 시각을 한 번에 교체
7. 목록·최근 변경·상태 문구 렌더링
8. 최신 호출인 경우에만 버튼 활성화

비교와 중복 제거는 `office-request-core.js`의 부작용 없는 순수 함수로 둔다. DOM 처리, 세션 및 요청 세대 관리는 `office-request.js`가 담당한다. API allowlist와 전송 본문은 `office-request-api.js`에서 바꾸지 않는다.

성공한 수동 새로고침마다 `recentChanges`는 새 비교 결과로 전부 교체한다. 변경이 0건이면 이전 변경 카드를 지우고 빈 상태를 표시한다. 실패하면 직전 성공 때의 변경 카드를 보존한다. 접수 생성·수정·취소와 `officeGet` 결과는 기존 목록 화면을 갱신할 수 있지만 비교 기준을 바꾸지 않으며, 다음 성공 수동 새로고침에서 직전 `officeList` 기준과 비교한다.

## 6. 개인정보와 보안 경계

- 비교 스냅샷에는 `requestId`, `status`, 검증된 시각만 둔다.
- 최근 변경 화면은 인증된 단지 안에서 사용자가 승인한 `receiptNo`, 동·호/공용 위치, 상태, 변경 시각만 표시한다. 비교 스냅샷에는 이 표시값을 복사하지 않는다.
- 입주민·담당자 이름과 전화번호, 상세 증상, 설명, 사진, 사진 URL·바이너리, 공개 금액, 완료 메모는 최근 변경 데이터나 화면에 복사하지 않는다.
- 기존 인증 세션의 `sessionStorage` 사용은 유지하지만, R1 비교 기준과 최근 변경을 `localStorage`, `sessionStorage`, IndexedDB, Cache API, Service Worker, URL 또는 history state에 저장하지 않는다.
- 최근 변경 자료를 `console`, analytics, clipboard 또는 네트워크 payload로 보내지 않는다.
- 사용자·서버 문자열은 `innerHTML`에 넣지 않고 `textContent` 또는 기존 안전한 DOM 생성 함수로만 렌더링한다.
- 기존 단지 세션이 허용한 `officeList` 범위를 넘어서는 조회를 추가하지 않는다.
- 로그아웃, 세션 만료, slug 불일치와 새 로그인 때 스냅샷·최근 변경·마지막 확인 시각을 즉시 초기화한다.

## 7. 오류와 동시성 처리

### 7.1 일반 실패

네트워크, HTTP, JSON, 설정 또는 일반 서버 오류가 발생하면 다음을 지킨다.

- 화면에 이미 있는 접수 목록을 비우지 않는다.
- 기준 스냅샷과 최근 변경 목록을 바꾸지 않는다.
- 마지막 성공 확인 시각을 유지한다.
- `새로고침하지 못했습니다 · 마지막 성공 HH:mm`처럼 실패와 마지막 성공을 함께 안내한다.
- 자동 재시도하지 않는다.

첫 조회부터 실패한 경우에는 기준을 만들지 않고 빈 목록과 오류 안내를 표시한다.

### 7.2 세션 만료

기존 `handleSessionExpired()` 경로를 사용한다. 세션 자료, 접수 목록, 상세 사진과 함께 R1 스냅샷·최근 변경·마지막 확인 시각을 지우고 PIN 로그인 화면으로 돌아간다.

### 7.3 응답 순서 역전

새 `listGeneration`은 현재 `sessionGeneration`과 함께 검사한다. 오래 걸린 이전 호출이 나중 호출보다 늦게 도착하면 그 응답은 목록, 기준, 최근 변경, 상태 문구와 버튼 상태를 바꾸지 못한다. 로그아웃 또는 다른 단지 로그인 뒤 도착한 응답도 같은 방식으로 폐기한다.

버튼은 요청 중 `disabled`와 `aria-busy="true"` 상태가 되고, 동일 버튼 연타는 추가 호출을 만들지 않는다.

### 7.4 잘못된 응답

기존 `office-request-api.js`가 HTTP 성공, JSON 객체와 `ok === true`를 확인한 응답만 컨트롤러에 넘긴다. 그 뒤에도 활성 session·slug와 최신 `sessionGeneration`·`listGeneration`이 모두 일치해야 적용한다. `response.requests`가 배열이 아니면 성공으로 적용하지 않는다. 빈 배열은 유효한 빈 목록이다. 일부 행만 잘못되었으면 잘못된 행을 제외하고 유효한 행으로 처리하되, 유효한 행이 전혀 없고 원래 배열이 비어 있지 않았다면 전체 응답을 잘못된 것으로 처리해 기존 상태를 보존한다.

## 8. 접근성과 반응형 기준

- 새로고침 버튼의 조작 영역은 최소 44px이다.
- 진행 중 버튼 문구와 비활성 상태를 시각적으로 표시한다.
- 최근 변경 요약 한 곳만 `aria-live="polite"` 또는 동등한 `role="status"`를 사용한다.
- 개별 변경 목록은 live region 밖에 두어 전체 목록 재렌더링 때 같은 변경을 반복 낭독하지 않는다.
- 새로 확인·상태 변경은 색상만으로 구분하지 않고 텍스트 라벨을 함께 표시한다.
- 새로고침 성공 후 사용자의 포커스를 강제로 이동하지 않는다.
- 긴 접수번호와 위치는 줄바꿈되며 가로 스크롤을 만들지 않는다.
- 390px 화면에서 새 접수 등록, 새로고침, 로그아웃과 필터 버튼이 겹치거나 잘리지 않는다.
- `prefers-reduced-motion` 기존 동작을 유지하고 새 애니메이션은 필수 정보 전달에 사용하지 않는다.

- `css/office-request.css`: 최근 변경 카드와 모바일·터치 스타일

- `js/office-request.js`: 메모리 상태, 수동 새로고침, 세대 검사와 렌더링
- `tests/office-request.logic.test.cjs`: 비교 순수 함수 검사
- `tests/office-request-recent-changes.e2e.cjs`: 새 기능 브라우저 검사
- `tests/office-request-auth.e2e.cjs`: 로그아웃·세션 만료 정리 회귀 보강
- `tests/office-intake.e2e.cjs`: 배포 workflow의 포털 검사 목록 계약 갱신
- `scripts/ensure-office-intake.mjs`: 자동 polling·외부 알림·영구 저장 금지 정적 검사

실제로 바뀌는 `office-request.css`, `office-request-core.js`, `office-request.js`의 `?v=` query는 하나의 새 캐시 표기인 `20260830-office-recent1`로 함께 올린다. 바뀌지 않는 자산의 query는 변경하지 않는다.

다음 파일과 시스템은 R1에서 변경하지 않는다.

- `js/office-request-api.js`
- `js/office-request-photo.js`
- `office-api.json`
- `privacy.html`
- `apps-script-contract/*`
- Apps Script OfficeIntake 배포와 저장소 버전
- `hyeonjang` 저장소, 현장 앱, `_현장.json`
- Google Drive 자료와 실제 관리사무소 접수 데이터
- SMS, 카카오톡, 이메일, Browser Notification 등 외부 전달 채널

```powershell
$env:NODE_PATH = 'C:\Users\1dncj\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules'
& 'C:\Users\1dncj\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' --test --test-concurrency=1 tests/office-request.logic.test.cjs tests/office-request-api.test.cjs tests/office-request-auth.e2e.cjs tests/office-request-workflow.e2e.cjs tests/office-intake.e2e.cjs
```

### 10.1 순수 로직

- 최초 목록은 기준만 만들고 변경 0건
- 새 `requestId`는 `이번 새로고침에서 새로 확인`
- 같은 ID의 상태만 변경된 경우 감지
- 상태는 같고 이전·현재 `updatedAt`이 모두 유효하며 현재 값만 증가한 경우 감지
- 동일 응답은 변경 0건
- 사라진 ID는 변경으로 추론하지 않음
- 50건 범위 밖으로 밀렸다가 다시 나타난 ID를 생성 시점이 확인된 신규 접수로 단정하지 않음
- 중복 ID에서 유효한 최신 행 하나 선택
- 누락·비정상·미래 시각은 시간 변화 근거에서 제외
- 입력 배열과 객체를 수정하지 않음
- 최대 10건 정렬과 초과 건수 계산

### 10.2 브라우저 흐름

- 로그인 첫 조회는 기준만 만들고 최근 변경을 표시하지 않음
- 로그인 초기 호출 이후 수동 새로고침 한 번은 `officeList` 호출 수를 정확히 1만 증가시키고 다른 action을 추가 호출하지 않음
- 새로 확인된 접수와 상태·내용 변경의 문구·정렬·건수 표시
- 현재 필터를 바꿔도 전체 응답 기준 비교 유지
- 상세 보기와 대시보드 복귀 뒤 기준 유지
- 일반 실패에서 기존 목록·기준·최근 변경·마지막 성공 보존
- 실패 뒤 회복한 성공 응답은 마지막 성공 기준과 비교
- 버튼 연타와 늦은 응답이 최신 화면을 덮지 않음
- 로그아웃·세션 만료·다른 slug 로그인에서 R1 메모리와 DOM 정리
- hard refresh 뒤 이전 변경을 다시 표시하지 않음
- 악성 receipt·위치·상태 문자열이 HTML로 실행되지 않음
- R1 자료가 브라우저 영구 저장소, URL, 로그와 clipboard에 남지 않음
- R1이 추가하는 자동 polling, 외부 provider 호출, 새 API action, 상태·금액·일정 쓰기가 없음
- 390px, 44px 터치 영역, 키보드, `aria-live`와 포커스 회귀

### 10.3 회귀·배포 검사

- 기존 관리사무소 포털 회귀 69개와 새 검사를 함께 통과
- `scripts/ensure-*.mjs` 전체 통과
- Pages 공개 허용목록 산출물 생성 및 검사 통과
- 새 E2E가 `Build public allowlist artifact`보다 먼저 실행됨
- 정적 HTML이 실제 변경 자산의 동일 cache-buster를 참조함
- `office-api.json`, Apps Script, hyeonjang 변경이 0건임을 diff로 확인

최소 변이 검증은 다음 보호 장치를 하나씩 되돌렸을 때 신규 검사가 실패하는지 확인한다. 이는 구현 작업 트리에서만 수행하는 일회성 로컬 증거이며 CI 필수 단계가 아니다. 변이 코드는 즉시 원복하고 커밋이나 공개 산출물에 남기지 않는다.

1. 성공 뒤 기준 스냅샷 교체 제거
2. 새로고침 실패 시 기존 목록 보존 제거
3. `listGeneration` 최신 응답 검사 제거
4. 로그아웃 시 R1 메모리 정리 제거

## 11. 작업 공간과 릴리스 경계

- 구현은 오래된 로컬 `manmool/main`이 아니라 최신 승인 기준점의 별도 clean worktree에서 진행한다.
- 현재 로컬 `manmool/main`의 `apps-script-contract/*` 기존 변경은 보존하고 R1에 섞지 않는다.
- 현재 Pages workflow는 `main` push 뒤에만 실행된다. 구현 계획에는 병합 전 같은 명령을 로컬에서 필수 실행하는 게이트를 넣는다.
- PR 전용 검증 workflow 추가는 권장 R0 안전 작업이지만 R1 사용자 기능과 섞지 않는다. 추가하려면 별도 범위와 승인을 받는다.
- 설계, 구현, 테스트, 로컬 커밋은 공개 배포 승인이 아니다.
- push, PR, merge, GitHub Pages 공개 배포는 완성본과 테스트 근거를 보고한 뒤 별도 승인을 받아 진행한다.
- 실제 관리사무소 PIN이나 운영 접수 자료 대신 합성 단지·접수 fixture만 사용한다.

## 12. 공개 배포 확인

별도 배포 승인을 받은 경우에만 다음을 확인한다.

1. `office.html`, `office-request.html`과 변경된 CSS·JS가 HTTP 200인지 확인
2. 공개 HTML이 `20260830-office-recent1` query를 참조하는지 확인
3. 기존 로그인과 `officeList` API 경로가 그대로인지 확인
4. 합성 시험 단지에서 첫 조회와 수동 새로고침을 한 번씩 확인
5. 자동 API 호출, Apps Script 재배포와 외부 알림 발송이 없음을 확인
6. 실제 운영 데이터가 생성·변경되지 않았음을 확인

## 13. 원복

문제가 생기면 R1 정적 포털 커밋과 해당 HTML cache-buster 참조를 함께 되돌린 뒤 Pages를 다시 배포한다. Apps Script, OfficeIntake 저장소, hyeonjang과 기존 접수 상태는 건드리지 않는다. 접수 자료를 삭제하거나 상태를 역전시키는 원복은 금지한다.

## 14. 완료 조건

- 관리사무소 직원이 현재 탭에서 수동 새로고침 전후에 새로 확인된 접수와 상태·내용 변경을 확인할 수 있다.
- 첫 성공 조회는 알림처럼 보이지 않고 기준만 만든다.
- 최근 변경 의미, 마지막 성공 시각과 오류 상태가 서로 구분된다.
- 개인정보 허용 목록, 메모리 전용 상태, 안전한 DOM 렌더링을 지킨다.
- 응답 경합, 세션 만료, 로그아웃과 잘못된 시각이 허위 변경이나 개인정보 재표시를 만들지 않는다.
- 신규 집중 검사, 기존 69개 포털 회귀, 전체 정적·Pages 검사가 모두 통과한다.
- 허용 파일 밖의 변경, API·서버·현장 앱 변경과 외부 발송이 없다.
- 공개 배포 전 별도 사용자 승인을 받는다.

## 15. 후속 확장과 비범위

R1이 안정화된 뒤에만 별도 설계로 다음 기능을 검토한다.

1. 서버에 보존되는 알림 이벤트와 읽음 상태
2. 정산 문서와 기간별 스냅샷
3. 직원별 개인 계정과 역할 권한
4. 자료 보완·일정 변경의 구조화된 대화
5. SMS·카카오톡·이메일 외부 알림

위 기능은 서버 저장소, 동의, 비용, 중복 방지와 권한 모델이 필요하므로 R1에 포함하지 않는다.

## 16. 설계 이후 절차
